## P0-1 拆分渲染层

**现状**

- `src/renderer/main.js` 263 KB / 6594 行，29 个 `renderX()`、83 个 `handleAction()` 分支、
  6 处内联 `style="`。
- 三份 CSS 合计约 193 KB，19 个 `!important`。

**目标**

- 按页面拆成 ES module，不引入 React/Vue；`main.js` 只保留启动、路由、事件分发和共享状态。
- 第一步只拆三个页面：模型配置、资料库、设置。

**验收标准**

- [ ] 每个页面一个模块，导出 `render()` 与 `handleAction()` 风格一致的接口。
- [ ] 第一步完成后 `main.js` 降到 3000 行以内，后续按页面继续下降。
- [ ] 现有单元测试和 18 条 E2E 全绿，PR 附 CI 链接。
- [ ] 不改动现有 DOM 结构、类名和视觉表现；拆分 PR 里不顺手改行为。

**预估**：3–5 天，拆成 3 个 PR。
**风险**：搬移过程中容易顺手改逻辑；每次 PR 只做搬移，行为变化单独开 PR。

## P0-2 失败路径测试包

**现状**

18 条 E2E 全部是正常路径；0.6.1 的下载器事故说明失败路径没有测试兜底。

**需要覆盖的失败路径（每类至少一条）**

- 从旧版原地升级，包括旧下载器本身有缺陷时的提示与手动安装引导。
- 备份损坏、备份生成中途中断、密码错误。
- 资料库根目录迁移中途失败与回滚。
- 并发写入 `workspace.json`。
- 磁盘满或目录无权限。
- 模型接口超时、429、断流。

**验收标准**

- [ ] 每类都有单元测试或 E2E，并且跑在 CI 里。
- [ ] 失败时用户能看到可理解的中文提示，不出现静默失败或卡死。
- [ ] 新增测试能复现对应缺陷，而不是只覆盖代码分支。

## P0-3 渲染层纳入类型检查

**现状**

`tsconfig.json` 只 include `src/main`、`src/preload`、`scripts`，且 `strict: false`。
最常改动、体量最大的渲染层完全不在类型检查范围内。

**验收标准**

- [ ] `src/renderer/main.js` 纳入 `allowJs` + `checkJs`。
- [ ] 先清零新增报错，再逐步打开 `strict`（可分 PR）。
- [ ] CI 的 `typecheck` 覆盖渲染层。

## P1-1 失败诊断包导出

**现状**

只有本地 `workbench.log`。用户报问题时，需要远程指导找日志路径，且日志目录可能已被更换。

**目标**

设置页提供「导出诊断信息」：日志尾部、应用版本、系统版本、主题与设置（脱敏）、
资料库路径概览，打成 zip 由用户自己保存，不上传。

**验收标准**

- [ ] 导出的包不含 API Key、模型 Key、绝对用户路径之外的隐私数据。
- [ ] 包内有一个 `README.txt` 说明每份文件是什么。
- [ ] 有单元测试覆盖脱敏逻辑。

## P1-2 启动耗时与性能基线

**现状**

没有启动耗时、包体积或大列表渲染的基准数据，性能回退无法被发现。

**验收标准**

- [ ] 启动到首屏可交互的耗时写入日志（已有 `Logger`，加打点即可）。
- [ ] 设置一个阈值，CI 或本机 `verify` 超阈值时告警，不直接失败。
- [ ] 记录一次 1000 条作业 / 1000 个资料文件的渲染耗时作为基线。

## P1-3 覆盖率门槛

**现状**

`npm test` 不采集覆盖率，"测试很多"和"关键路径被测到"是两回事。

**验收标准**

- [ ] 用 Node 内置 `--experimental-test-coverage` 或等价方案产出覆盖率。
- [ ] 先记录现状，不设门槛；稳定后再对 `src/main` 设一个只升不降的门槛。

## 推进规则

1. 一次只做一项，开 `codex/*` 分支，走 PR，CI 过了再合。
2. 每项完成后更新本文件的「状态总览」，并在 `docs/HANDOFF.md` 留一行记录。
3. 不为了清债务做一次性大爆炸重构；每步都保持可发布。
