# ZP Workbench 开发框架

## 1. 目标

本框架用于把 ZP Workbench 从可运行的产品原型发展为可长期维护、可发布、可回滚的
正式 Windows 工作站。

正式工程不只看功能是否存在，还必须满足以下条件：

- 每次修改都可追踪、可审查、可测试。
- 每次构建都可重复，不依赖开发者电脑的临时状态。
- 每个用户数据格式都有版本和迁移路径。
- 每次发布都可验证、可回滚，并保留明确的更新说明。
- 每个故障都能通过日志和诊断信息定位。
- Agent 生成的代码没有特殊待遇，必须经过与人工代码相同的门禁。

## 2. 分支与协作模型

### 目标分支

| 分支          | 用途               | 规则                         |
| ------------- | ------------------ | ---------------------------- |
| `main`        | 稳定、可发布代码   | 受保护，只能通过 PR 合并     |
| `codex/*`     | Agent 开发分支     | 短生命周期，对应一个明确任务 |
| `feature/*`   | 人工功能分支       | 短生命周期，完成一个功能     |
| `fix/*`       | 缺陷修复分支       | 必须包含回归测试             |
| `release/x.y` | 大型版本的发布准备 | 仅允许修复发布阻塞问题       |

当前仓库仍使用 `v3` 作为开发主线。迁移到正式流程时，应把稳定版本转移到受保护的
`main` 分支，再逐步停止直接向 `v3` 提交。

### 标准开发流程

1. 从 Issue 或明确需求生成任务描述。
2. 明确验收标准、风险、数据影响和回滚方式。
3. 从 `main` 创建 `codex/*`、`feature/*` 或 `fix/*` 分支。
4. 小步提交，保持每次提交可以理解和审查。
5. 补齐单元测试或端到端测试。
6. 创建 PR，填写变更、测试、风险和截图。
7. CI 检查全部通过后再进行人工验收。
8. 合并到 `main`，删除短生命周期分支。
9. 按发布流程创建版本标签和 GitHub Release。

禁止直接把未经验证的功能提交到稳定分支，也禁止移动或覆盖已经发布的版本标签。

## 3. 环境与可重复构建

当前要求：

- Windows 10 或 Windows 11，x64
- Node.js `24.x`
- npm `11.x` 或 `12.x`
- 所有依赖通过 `package-lock.json` 固定

当前已补充：

- `.node-version`
- `package.json` 中的 `engines` 和 `packageManager`
- `npm ci` 作为 CI 和本地验证的统一安装方式

任何依赖升级都必须单独提交，并说明升级原因、兼容性和验证结果。

## 4. 架构边界

### 主进程

目录：`src/main/`

职责：

- 文件系统访问
- 本地数据持久化
- DeepSeek Harness 安装、启动和停止
- 更新检查和下载
- 系统通知、托盘、窗口和进程生命周期
- IPC 参数验证

主进程是唯一允许直接访问文件系统和启动本地进程的层。

### Preload

目录：`src/preload/`

职责：

- 只暴露白名单 API
- 将 IPC 封装为 `window.launcher`
- 禁止向渲染层暴露 Node.js、文件系统或任意 IPC 通道

新增 IPC 时必须同时完成：

- 主进程处理函数
- Preload 白名单
- 渲染层调用封装
- 输入验证
- 错误处理
- 自动测试

### 渲染层

目录：`src/renderer/`

职责：

- 页面与组件
- 用户交互状态
- 数据展示
- 不直接访问文件系统或 Node.js

当前渲染层仍是较大的单体文件。目标结构：

```text
src/renderer/
  app/
    bootstrap.js
    router.js
    state.js
  features/
    schedule/
    assignments/
    experiments/
    knowledge/
    updates/
    settings/
  components/
  services/
  styles/
```

拆分顺序应先从独立功能开始，例如更新、课表和资料库，不应一次性重写全部界面。

### 数据层

本地数据至少包括：

- `settings.json`
- `workspace.json`
- 工作区备份
- 启动器日志
- DSH 运行时和用户配置

数据写入必须满足：

- 临时文件写入后原子替换
- 修改前自动备份
- 损坏文件不能导致应用直接崩溃
- 新版本读取旧数据时必须执行正式迁移

## 5. 数据版本与迁移

数据迁移不能依赖应用版本号猜测。每个持久化文件应具有独立的 `schemaVersion`。

迁移规则：

1. 读取文件并识别版本。
2. 如果版本高于当前客户端，停止写入并提示用户升级应用。
3. 按顺序执行 `v1 -> v2 -> v3` 迁移。
4. 迁移前创建带时间戳的备份。
5. 迁移后执行结构校验。
6. 校验失败时恢复备份，并保留迁移诊断日志。

每项迁移都必须有：

- 旧版本数据夹具
- 预期新结构
- 单元测试
- 失败回滚测试
- 对应发布说明

## 6. 测试体系

### 单元测试

验证纯逻辑：

- 课表解析
- 周次和节次计算
- 数据规范化
- 更新版本比较
- 文件路径和分组规则

### 集成测试

验证模块协作：

- WorkspaceStore 读写与备份
- DSH 安装和状态读取
- 更新清单合并与下载回退
- 实验资料导入
- 设置修改

### 契约测试

验证 IPC：

- 每个通道的参数类型
- 非法参数拒绝
- 错误信息可理解
- Preload 不暴露多余能力

### 端到端测试

使用 Playwright Electron 至少覆盖：

1. 首次安装启动和欢迎页。
2. 完成 API 与模型配置。
3. 导入 WPS 和 PDF 课表。
4. 编辑、删除和恢复课程。
5. 导入实验资料并生成知识点。
6. 检查更新、模拟下载失败、切换线路和校验失败。
7. 创建备份、破坏数据、恢复备份。
8. 从上一稳定版升级到新版本。

### 发布冒烟测试

每次正式发布前，在干净的 Windows 用户环境执行：

- 全新安装
- 首次启动
- 覆盖安装
- 检查更新
- 下载与 SHA-256 校验
- 卸载
- 重新安装

## 7. 质量门禁

### PR 必须通过

- `npm ci`
- ESLint
- Prettier 或等价格式检查
- JavaScript 类型检查
- `npm test`
- Electron 端到端冒烟测试
- 生产构建
- 依赖安全审计
- 安装包最小构建验证

### 发布必须通过

- 所有 PR 门禁
- 数据迁移测试
- 更新下载和回退测试
- 安装、覆盖安装和卸载测试
- 安装包数字签名验证
- 更新清单和 SHA-256 验证
- Release 文件数量与名称检查

当前已有 52 项自动测试，并已具备静态检查、类型检查、Electron E2E、生产构建和
运行时依赖审计门禁。代码签名、数据迁移测试和更新清单签名仍属于后续发布阶段。

## 8. 安全与隐私

必须保持：

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`
- 严格 CSP
- IPC 白名单
- 外部 URL 协议验证
- 禁止渲染层任意读写本地文件

后续必须补充：

- Authenticode 代码签名
- 更新清单 Ed25519 签名
- SBOM 和第三方许可证清单
- 依赖审计和修复时限
- 日志脱敏规则
- API Key 和用户配置的存储边界说明
- 隐私说明和数据删除说明

### 依赖风险规则

- Critical：立即停止发布并修复。
- High：当前迭代内修复或给出不可达证明。
- Moderate：进入计划，不允许无限期忽略。
- Low：随常规升级处理。

## 9. 日志、崩溃与诊断

当前日志系统只记录主进程文本日志。目标应包含：

- 结构化的应用版本、系统版本和事件字段
- 主进程 `uncaughtException` 和 `unhandledRejection`
- Electron `render-process-gone` 和 `child-process-gone`
- 更新检查、下载线路、校验和安装结果
- DSH 安装、启动、退出和端口冲突信息
- 日志轮转和最大磁盘占用

应用内应提供“导出诊断包”，默认去除 API Key、Token、Cookie 和用户文档正文。

崩溃上报必须遵守用户同意原则。正式阶段可以接入 Sentry 或其他错误平台，但需要
明确数据范围、保留周期和关闭方式。

## 10. 发布与回滚

### 版本规则

- `0.x`：产品结构和数据仍可能变化。
- `1.0.0`：数据迁移、安装更新、签名、诊断和支持流程达到稳定标准。
- Patch：修复，不增加破坏性变更。
- Minor：兼容性新功能。
- Major：需要迁移或改变用户工作方式。

### 发布流程

1. 完成功能和文档。
2. 冻结版本，进入发布候选阶段。
3. 执行完整测试和干净环境冒烟测试。
4. 更新版本号和发布说明。
5. 合并发布 PR。
6. 创建不可变标签，例如 `v0.4.0`。
7. GitHub Actions 构建、验证、签名并上传。
8. 先向内部或测试用户发布，再扩大范围。
9. 监控至少一个稳定周期。
10. 将当前版本标记为最新稳定版。

### 回滚

必须始终保留上一个稳定版本的安装包、清单和校验值。

回滚触发条件：

- 启动失败率明显上升
- 数据迁移错误
- 更新循环或无法启动
- 安装包签名或校验异常

回滚不是删除新版本，而是把 `latest.json` 重新指向已验证的上一稳定版本，并发布
故障说明。

## 11. Definition of Done

一项功能只有同时满足以下条件才算完成：

- 行为符合验收标准
- 有自动化测试
- 错误状态有用户可理解的提示
- 不破坏本地数据
- IPC 和权限边界正确
- 日志足以定位失败
- 文档或帮助内容已更新
- 构建和测试通过
- 用户已完成人工验收

## 12. 分阶段路线

### 阶段 A：工程基线

目标：停止依赖人工记忆维持质量。

1. 建立受保护的 `main` 和 PR CI。
2. 增加 ESLint、Prettier 和类型检查。
3. 建立第一组 Playwright Electron 冒烟测试。
4. 建立发布 PR、发布检查和回滚清单。

完成标准：

- 任何新 PR 都无法跳过自动测试。
- 课表导入、启动、设置保存和更新检查至少各有一个 E2E 用例。
- 发布流程不依赖开发者手工判断文件是否完整。

### 阶段 B：正式发布能力

目标：让普通用户可以安全安装和升级。

1. Authenticode 代码签名。
2. 数据迁移框架和跨版本夹具。
3. 崩溃处理与诊断包。
4. SBOM、许可证和依赖审计门禁。
5. 自有 CDN 和更新清单签名。
6. 稳定版、测试版和灰度更新。

完成标准：

- Windows 不再显示未知发布者。
- 任意支持版本都能无损升级到当前版本。
- 更新失败不会破坏现有安装。
- 可以回滚 `latest.json` 并阻止问题版本继续分发。

### 阶段 C：1.0 准备

目标：形成可长期维护的产品。

1. 按功能拆分渲染层。
2. 建立性能、无障碍和长时间运行测试。
3. 建立问题反馈、版本支持和安全响应流程。
4. 明确隐私、许可证、数据和卸载行为。
5. 建立发布节奏和兼容性承诺。

完成远端保护配置后，再开始新的功能开发或界面重构。
